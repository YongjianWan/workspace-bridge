# agent 参与的离线对照回放（agent-ab）

本实验回答一个现有证据答不了的问题：agent 已经改完一个文件、还要找「这次还得一起改哪些文件」时，把 `impact` 的输出交给它，能不能比它只靠 grep、读文件、看 git 历史和编译多找回该一起改的文件。

2026 年 10 月 23 日状态：设计写完，harness `eval/agent-ab.js` 和测试写完，在预实验的 4 个提交上用桩 agent 跑通了不花钱的 dry run；预实验本身没有跑，等项目所有者答复凭据和预算。详见第 10 节。

本文的实验代号是 agent-ab，口径版本 v1。J1、F1、P1 是项目所有者的私有仓库代号，含义见 [ROADMAP.md](../ROADMAP.md) 5.1；本文只出现代号和汇总数字，提交哈希、路径和逐条明细只存放在 gitignored 的 `eval/truth/agent-ab/`。

## 1. 为什么要做

现有证据只说明 `impact` 的列表本身比笨基线好，没说明它对 agent 有用：

- **列表对列表。** J1 的 20 个留出提交上，Java→Java 前 15 召回：工具 0.6545、笨基线 0.5034（笨基线是只看历史共改加主干名的办法，定义见 ROADMAP 5.2）。按提交配对 bootstrap（方法见第 5 节），增益 +15.1pp（pp 即百分点），95% 区间 [+6.2, +25.0]pp。这组数是 2026 年 10 月 22 日用 `eval/truth/replay/J1-holdout-diffctx-v4/runs.jsonl` 重算的实测，与 SESSION.md 记录一致。但这 20 个提交被 15 个排序变体反复用来挑方案，已经不是独立样本。
- **没有 agent 参与。** 回放比的是两份列表，不是「agent 自己找」与「agent 拿到列表后再找」。agent 自己会 grep 类名、读调用方、看 `git log`，列表里的很多文件它不靠工具也能找到。
- **唯一的 A/B 测不到这个问题。** U-23（CHANGELOG 有记录）的任务点名了目标文件，两组都是 5/5，测的是「改对」，不是「找全」。
- **真实使用记录为零。** ROADMAP 第 7 节 T2.1 未开始，改代码时调用 `impact` 的日志一条都没有；T2.2（同模型带工具、不带工具对照）计划过，没执行。

外部同类工作（Microsoft CodePlan、TDAD）的端到端评估看漏改数和回归率，不看任务解决率。本实验是 T2.2 的低成本前置：只测「找全」，不让 agent 真改代码，所以几十个提交、两三百次 agent 运行就能出结论。

## 2. 一次试次怎么做

一次试次 = 一个提交 C、它的一个输入文件、一种条件、一次 agent 运行。

**工作区。** 克隆目标仓库，`git reset --hard <C 的父提交 P>`，按 ROADMAP 第 7 节 T2.2 的做法切断更晚的历史：`git remote remove origin`、删除标签和其他分支、`git reflog expire --expire=now --all`、`git gc --prune=now`。P 及更早的历史保留，C 及之后的提交不可达。然后把输入文件替换成它在 C 里的内容，留作未提交改动。这就是「agent 刚改完这个文件」的状态，`git diff` 能看到这处改动。J1 的路径很深，克隆必须带 `-c core.longpaths=true`；放在较长的临时目录下，不带这个参数会报 `Filename too long`，检出失败。2026 年 10 月 22 日在会话临时目录实测复现过。

**任务。** 两种条件的提示词正文相同：

```text
这个仓库的工作区里，<输入文件路径> 已经改完，改动可以用 git diff 查看。
为了让这次改动完整，还有哪些已经存在的文件需要一起修改？
只列你判断需要修改的文件，不列只需阅读的文件，不列新文件，最多 15 个，按把握从高到低排列。
不要修改任何文件。最后只输出 JSON：{"files": ["相对仓库根目录的路径", ...]}
```

提示词不给提交说明。提交说明是任务意图，常直接点名要改的类，会同时帮到两组、压小差值；工具本身也不读意图。这条取舍对结论方向的影响见第 9 节。

**条件 A（agent 自带能力）。** 可用工具：读文件（Read）、文本搜索（`grep`、`rg`、`find`、`ls`）、只读 git 命令（`git log`、`git show`、`git diff`、`git blame`、`git grep`），以及 J1 的离线编译（本节末尾「编译」一段）。A 的提示词里不出现本工具。

**条件 B（A 加 `impact`）。** 工具与 A 完全相同。区别只有一处：harness（驱动实验的脚本）先在同一个工作区里运行 `node cli.js impact --cwd <工作区> --file <输入文件> --json --quiet`，把标准输出原样接在提示词后面，前面加一行「下面是依赖分析工具对这个文件的输出，可作参考：」。工作区有未提交改动，`impact` 会自动读 `git diff HEAD` 做 diff 上下文排序，这正是 agent 改完一个文件后调用它的真实形态。B 不自己运行 CLI，这样差值只反映列表里的信息，不掺杂「agent 会不会用这个 CLI」。

**git 历史给两组都开放。** 最初的实验要求里，A 只有 grep、读文件和编译；本设计给两组都加了只读 git。原因是 `impact` 的候选里有历史共改，A 没有 git 时，B 的增益里会混进「能看历史」这一项，而真实 agent 本来就能跑 `git log`。这样设比较保守：工具要胜过一个能自己挖历史的 agent。项目所有者要改回不给 git 时，在开跑前改第 8 节口径。

**公共设置。** 两组都用 `claude -p`（Claude Code 的无交互模式），参数相同：

| 设置 | 取值 | 为什么 |
|---|---|---|
| 模型 | `claude-opus-5-5`，`--effort medium` | 项目所有者日常改代码用 Opus；medium 是该模型的默认档 |
| 上下文隔离 | `--bare`、`--disable-slash-commands`、`--strict-mcp-config`（不给 MCP）、`--no-session-persistence` | 不加载用户 CLAUDE.md、记忆、skill 和 hook；否则 workspace-audit skill 和用户记忆会同时进入两组 |
| 工具 | `--tools Read,Grep,Glob,Bash`，Bash 只放行上面列的搜索命令、git 子命令和编译命令（`--allowedTools` 规则），`--permission-prompts none` 让其余调用自动拒绝 | 两组工具面一致，A 碰不到全局安装的 workspace-bridge-cli |
| 网络 | 去掉 `ANTHROPIC_BASE_URL`，直连 API | 本机这个变量指向 Headroom 压缩代理，它会改写 agent 看到的工具输出和 token 数 |
| 预算 | `--max-turns 40`、`--max-budget-usd 3` | 防止单次失控 |
| 输出 | `--output-format stream-json --verbose`，轨迹逐次存档 | 留完整轨迹和用量，单次可回放 |

2026 年 10 月 23 日在没有凭据的环境里用这组参数实际起了一次 `claude -p`：参数全部被接受（`--max-turns` 不在 `--help` 里，但能用），会话停在认证失败，`total_cost_usd` 为 0。初始化事件显示 `--bare` 下 agent 只有 Bash 和 Read 两个工具，没有 Grep、Glob，所以搜索命令必须在 Bash 放行清单里，否则 A 只剩 `git grep`。同一事件里还能看到 `--bare` 照样加载了内置插件，但不执行插件 hook。harness 把每次运行实际拿到的模型、工具清单和是否直连记进运行记录，事后能核对两组设置一致。

J1、F1 仓库根目录都有自己的 `AGENTS.md` 和 `CLAUDE.md`。`--bare` 不会自动加载它们，agent 自己去读时，读到的是仓库本来的约定；2026 年 10 月 23 日按 cutoff 版本计数，四个文件里提到本工具的次数都是 0，不会偏向任何一组。

`--bare` 只认 `ANTHROPIC_API_KEY`（按 token 计费），不读订阅登录。只能用订阅时，`run` 加 `--no-bare`，并给 harness 一个干净、登录过的 `CLAUDE_CONFIG_DIR`（需要项目所有者登录一次）；这时 agent 会多出 Grep、Glob 两个工具，也会加载仓库的 `CLAUDE.md`，两组仍然相同，但结果要注明用的是哪种模式。

**编译。** J1 是 Maven 项目，本机有 `mvn` 和 JDK 21，`~/.m2/repository` 已有依赖缓存。2026 年 10 月 22 日在 cutoff 提交的临时克隆上实测，`mvn -o -q -DskipTests compile` 退出码 0，冷编译 208 秒，输出里只有 lombok 触发的 JDK 弃用警告。所以 J1 两组都放行这条编译命令。冷编译三分多钟会拖慢每次试次，harness 建工作区时先编译一次，复制工作区时保留 `target/` 和文件时间，agent 再编译时走增量。出现编译失败或单次超过 5 分钟的工作区，该提交两组都不给编译，并在结果里记明。F1 是没有 TypeScript 的 Vue 项目，`package.json` 没有类型检查脚本，`vite build` 只能查出缺失的 import，两组都不给。

## 3. 样本

### 3.1 正式样本池：只用新鲜提交

新鲜提交指从未进过任何回放或探针的提交。回放样本有一个截止提交（cutoff），记在 `eval/truth/targets.json`，三个仓库都在 2026 年 8 月 12 日；所有回放只取 cutoff 及更早的提交，每个仓库再留出时间上最新的 20 个可用提交不回放（留出池）。2026 年 10 月 22 日用 `eval/replay-impact.js` 的 `isStatFile`、`selectSamples` 按 ROADMAP 5.2 口径（非合并、2 到 20 个统计文件、至少一个输入真值非空）实测：

| 来源 | 可用提交数 | 统计文件 ≥ 3 个（新增文件不算）的提交数 | 说明 |
|---|---:|---:|---|
| J1 cutoff 之后 | 6 | 6 | 本地仓库 HEAD 停在 2026 年 8 月 24 日 |
| F1 留出池 | 20 | 16 | 所有 F1 回放都带 `--holdout 20`，这 20 个从未被回放 |
| F1 cutoff 之后 | 7 | 3 | 本地仓库 HEAD 停在 2026 年 9 月 4 日 |
| J1 留出池 | 20 | 15 | **不用**：已被 15 个排序变体反复用来挑方案 |
| P1 | 0 | 0 | 本地仓库 HEAD 就是 cutoff |

正式样本池合计 33 个提交（J1 6 个、F1 27 个）。池子偏 F1，主场景 J1 只有 6 个；原因是本地仓库很久没有拉取。项目所有者在业务仓库原地 `git pull` 后，cutoff 之后的提交会变多，样本池在开跑前重新冻结一次（第 8 节）。

**还没决定的事：F1 留出池给不给本实验用。** ROADMAP 5.2 把它留给 T2.2 当任务。本实验就是 T2.2 的前置：结论是「无增量」时 T2.2 多半不会再开；结论是「有增量」时，T2.2 改用开跑时更新的提交。建议给本实验用。由项目所有者在开跑前决定；不给时，正式样本池只剩 13 个提交，按第 6 节推算不够用，要先拉取新提交。

### 3.2 预实验样本：用已经用过的提交

预实验只测方差和成本，不判增量，所以用已经被回放用过的提交，把新鲜提交全部留给正式实验。规则：J1、F1 各取留出池之前、时间上最近的 2 个提交，要求统计文件 ≥ 3 个（新增文件不算）且至少有 2 个修改（M）状态的输入。离留出池最近，代码状态最接近正式样本。

### 3.3 每个提交取哪些输入

输入限于 C 中修改（M）状态、真值非空的统计文件；删除（D）状态的文件在工作区里不存在，没法当「刚改完的文件」。候选按 `sha256(提交哈希 + ":" + 路径)` 升序排列，取前 m 个（m 见第 6 节）。规则不看文件内容和真值，事先就能算出，避免挑容易的输入。

真值沿用 ROADMAP 5.2：同一提交中除输入以外的统计文件，去掉新增文件。正式样本池按 m = 3 封顶约有 91 个输入，不封顶约 168 个；这两个数含删除状态的文件，实际可用的输入会略少。

## 4. 指标

每次试次算以下几项：

- **召回率**：真值文件中，agent 最终列表命中的比例。
- **精确率**：列表中命中真值的比例；空列表不计入精确率平均，单独报告空列表占比。
- **多报数**：列表中不在真值里的文件个数（FP）。仓库里不存在的路径算多报，另外单独计数。
- **前 5 召回**：只看列表前 5 个，用来排除「B 列得更长」带来的召回。
- **用量**：输入、缓存读、缓存写、输出 token，美元成本（`claude -p` 的 JSON 输出里有），轮数，墙钟耗时。

路径比较前统一成正斜杠、去掉开头的 `./`，再按 P 的 `git ls-files` 做大小写不敏感的回查，换成仓库里的真实写法。真值里的非统计文件（yml、sql 等）被列出时不算命中，也不算多报，只记录。

每个提交先对各输入、各次运行取平均，得到 A、B 各一个召回率，再求差值 d = B − A。汇总时每个提交权重相同，和 ROADMAP 5.2 的两级平均一致。

同一批输入上另外算一个参照列，不参与判定：`impact` 列表单独的召回（就是 B 拿到的那份，`impact` 输出的绝对路径先换成相对路径）。三列对照能看出 B 是否只是照抄工具，A 是否本来就超过工具。

## 5. 主分析与通过条件

**主分析。** 对提交级差值 d 求平均，按提交做配对 bootstrap：有放回抽提交，10,000 次，种子 20261022，取 2.5% 和 97.5% 分位作为 95% 区间。J1、F1 分开报告，但只用合并结果判定。

**判定。** 三条事先写死：

| 结论 | 条件 | 下一步 |
|---|---|---|
| 有增量 | d 的均值 ≥ +5pp，95% 区间下界 > 0，且 B 比 A 每输入平均多报不超过 3 个文件 | 值得开 T2.2 真任务对照；SKILL.md 可以把「改完第一个文件后跑 impact」写成推荐用法 |
| 无增量 | d 的 95% 区间上界 < +5pp | 当前形态的 `impact` 对这个 agent 没有找全上的增量；项目所有者在 C1（给证据不排序）和停止产品化投入之间决定 |
| 不确定 | 其余情况，包括召回过线但多报超线 | 照实报告；不看结果追加样本，要扩样本就开 v2，事先写死新样本量 |

+5pp 是「值得改工作流」的最低增益。J1 Java→Java 每个输入的真值中位数是 5 个文件（ROADMAP 第 6 节诊断），按这个数算，+5pp 约等于每 4 个任务多找回 1 个文件。这条线是判断，不是测出来的；项目所有者要调整，必须在正式开跑前改。多报上限 3 个沿用 T2.2 的多改上限，防止 B 靠把 15 个候选全抄进来抬召回。

## 6. 样本量与每条件次数

**方差从哪来。** 提交级差值 d 的方差由三部分组成：

```text
Var(d) = σ_c² + σ_in² / m + 2 × σ_run² / (m × k)
```

σ_c 是增益在提交之间的差异，σ_in 是同一提交内不同输入之间的差异，σ_run 是同一输入、同一条件重复运行的波动；m 是每提交输入数，k 是每输入每条件运行次数。

**已有数据给出的代理。** 回放里没有 agent，但「工具 − 笨基线」的提交级差值结构相同，可以先估前两项。2026 年 10 月 22 日从已有 `runs.jsonl` 实测：

| 回放 | 提交数 | 所有输入平均时 d 的标准差（SD） | 每提交只取 1 个输入时 d 的标准差 |
|---|---:|---:|---:|
| J1 留出 20 提交，Java→Java | 20 | 22.2pp | 35.6pp |
| J1 非留出，Java→Java | 75 | 30.4pp | 36.8pp |
| F1 非留出，全部类型 | 144 | 25.4pp | 33.3pp |

这三组回放每提交约 5 到 6 个输入，按 m = 5、σ_run = 0 代入上式反推，三组分别得 σ_c 约 17、29、23pp，σ_in 约 31、23、24pp。这是推算，只用来定量级。结论有两条：输入之间的差异和提交之间的差异在同一量级，所以每提交多取几个输入比多跑几次更省样本；m = 3、不计运行波动时，d 的标准差约 25 到 32pp，这也是推算。

**样本量公式。** 要在双侧 5%、把握度 80% 下检出真实增益 δ，需要的提交数为 n = ⌈(2.8016 × SD / δ)²⌉。按公式推算：

| d 的标准差 | δ = 10pp | δ = 15pp |
|---:|---:|---:|
| 15pp | 18 | 8 |
| 20pp | 32 | 14 |
| 25pp | 50 | 22 |
| 30pp | 71 | 32 |
| 35pp | 97 | 43 |

正式样本池现在是 33 个提交，能检出的最小增益约为 0.49 × SD：SD = 25pp 时约 12pp，SD = 30pp 时约 15pp，同样是推算。参照量是工具对笨基线的 +15pp：33 个提交大致能检出同量级的增益，检不出更小的。

**怎么定 m 和 k。** 预实验测出 σ_run 后按以下规则定，写进口径后不再改：

1. m = min(3, 该提交可用输入数)。
2. σ_run² ≤ σ_in² / 4 时 k = 1，否则 k = 2。
3. σ_c、σ_in 取三组代理的中位数（23pp、24pp），σ_run 取预实验实测值，代入上式算出 SD，再代入样本量公式求 δ = 15pp 时的 n。按公式推算，m = 3 时：σ_run = 10pp 对应 k = 1、SD 约 28.1pp、n = 28；σ_run = 15pp 对应 k = 2、SD 约 28.2pp、n = 28；σ_run = 30pp 对应 k = 2、n = 36。n ≤ 样本池时用全部样本池；n > 样本池时，先由项目所有者拉取新提交，样本池够了再开跑。

## 7. 预实验

**做什么。** 第 3.2 节的 4 个提交，每提交 2 个输入，每输入每条件跑 3 次，共 4 × 2 × 2 × 3 = 48 次。A、B 按输入交错、随机顺序运行，避免服务端模型在时间上漂移只影响一组。

**测出什么。** σ_run（16 个单元、每单元 3 次，自由度约 32，估得比较稳）；单次 token 与美元成本、轮数、耗时；无效运行的比例和原因（没输出合法 JSON、超轮数、访问了工作区以外的路径）。σ_in、σ_c 在预实验里只有 3 到 4 个自由度，只用来检查代理是否在同一量级，不替代代理。

**能不能开正式实验。** 三条都满足才开：

1. 合法输出 ≥ 90%（48 次里至少 44 次）。
2. 单次成本中位数 ≤ 3 美元。
3. 按第 6 节算出的 n 不超过开跑时冻结的样本池，或项目所有者已经拉取到足够的新提交。

**成本。** 单次运行的 token 量是估的：Claude Code 自带的系统提示和工具定义约 1.5 到 2 万 token，一次「找相关文件」约 15 到 30 轮，上下文逐轮增长、大部分走缓存。按 Opus 5.5 定价（输入每百万 token 4 美元，缓存读 0.2 美元，输出 20 美元，取自 claude-api 技能 2026 年 10 月 6 日缓存的价目表）估单次约 0.7 美元，区间 0.3 到 2 美元。预实验 48 次约 34 美元（区间 15 到 100 美元），正式实验按 33 个提交、约 91 个输入、k = 1 算约 182 次、130 美元（区间 55 到 360 美元），k = 2 时翻倍。这些都是估算，预实验测出真实单价后重算。用订阅额度而不是 API key 时，不产生账单，但占用同一账号的额度。

## 8. 事先登记的口径（agent-ab v1）

以下各项在正式开跑前冻结，写进 `eval/truth/agent-ab/protocol.json`，并记录本文件的 SHA-256。任何一项要改，口径升 v2，正式实验从头跑，v1、v2 的数字不比较。

1. 样本池：开跑当天按第 3.1 节重新列出新鲜提交，写入哈希清单；之后不增不减。
2. 输入：第 3.3 节的哈希排序规则，m 按第 6 节。
3. 提示词：第 2 节正文逐字固定，B 的附加块格式固定；记录两份提示词的 SHA-256。
4. 模型与参数：第 2 节表格，含 `claude --version` 输出。
5. 次数：k 按第 6 节。
6. 指标、主分析、判定：第 4、5 节。
7. 无效运行：没输出合法 JSON、超轮数、超预算、读到工作区以外路径（Read、Grep、Glob 的路径参数，以及 Bash 命令里的绝对路径；被权限拒绝的调用不算）、改动了已跟踪文件的运行记为无效，原样保存，同一试次重跑一次；重跑仍无效的，该试次召回按 0 计、计入无效数。两组无效率相差 10 个百分点以上时，在结论旁写明。环境问题不算无效运行：进程起不来、没有结果事件、或者出错且花费为 0（模型没跑，比如没登录、断网）时，harness 不写 `runs.jsonl`，记进 `infra-errors.jsonl` 后整轮停下，修好后用同样的命令接着跑。超时不属于环境问题，agent 已经跑了、花了钱，按无效运行计。
8. 不中途看结果：正式运行结束前不计算 d；不按结果换输入、换提示词或追加样本。

## 9. 结果能说明什么、不能说明什么

- **离线没有任务意图，结论是不对称的。** agent 只看到 diff，看不到任务目的，比真实工作时弱。「无增量」是强证据：没有意图时工具都帮不上，有意图时更帮不上。「有增量」只说明列表里有 agent 自己没找到的信息，真实工作中能否减少漏改，仍要 T2.2 验证。
- **真值有噪声。** ROADMAP 5.6 的漏报归因里，约三分之一的漏报文件和输入没有任何结构关系（⑧ 真值噪声）。这类文件两组都很难找到，会压低两组的召回，但不偏向任何一组。
- **只测一个模型。** 结论限于 `claude-opus-5-5` medium 档；换模型或换 harness 要重测。
- **只测找全，不测改对。** agent 不改代码，回归率测不到。
