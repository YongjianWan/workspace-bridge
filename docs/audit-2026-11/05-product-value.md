# 05 产品价值与范围

结论见 [README.md](./README.md)。规模数字为实测，最小核心的体量为 require 正则估算（含惰性 require，略偏大）。

## 规模

- `src/` 203 个 JS 文件、约 41,000 行；`test/` 390 个文件、53,300 行；`eval/` 70 个文件、11,400 行；`scripts/` 10 个文件、1,700 行。测试代码比产品代码还多。
- 分层行数：依赖图引擎顶层 7,100，工具层 5,400，服务顶层 4,200，工具函数 4,700，CLI 5,900。
- 9 种语言，各语言的 parser、resolver 与框架查询共约 9,800 行，占 `src/` 的 24%。
- 命令：`--help` 列 14 个主推命令，`--help --all` 共约 30 个。
- 2026 年 3 月 27 日起 679 个提交，其中文档 245 个、修复 161 个、功能 122 个（此处口径与 [01](./01-history-and-process.md) 的分类规则略有出入，以 01 为准）。

## 有评测证据的只有一条线

宣称的能力是 9 种语言、约 30 个命令，有评测证据的是 `impact`（含 diff-context 与共改）、`affected-tests`、`dead-exports`。

- `impact`：J1 留出 20 个提交，Java→Java 召回 0.6545，笨基线 0.5034，差 15.1 个百分点，95% 区间 [+6.2, +25.0]。这个数只来自一个私有仓库的 20 个提交，15 个排序变体都在这批提交上选过方案。diff-context 在 F1 +5.9 个百分点、P1 +2.8、J1 +2.2。
- `affected-tests`：typer 召回 0.99、精确率 0.548。
- 过线线 0.70 未达到，算法排序通道已全部关闭。
- 以下命令多半是「为完整而有」（判断，不是实测）：`audit-security`（Semgrep 包装，与 AGENTS 自己写的「结构分析不等于语义分析」冲突）、`api-contracts`（路径级匹配，字段级契约未验证）、`query-*`、`stats`、`debug`、`health`、`dependencies`、`dependents`（SKILL 里写了「避免调用」）、`audit-map`、`watch`、`guard`（没有评测）。`dead-exports` 在 Java 与 Spring 上误报高，AGENTS 自己写了「别当 KPI」。

## 对 agent 的实际效果：没有证据

- `impact` 的使用日志为零，T2.1 没有开始，ROADMAP 2.3 节这样记录。
- U-23 是 5 个任务、两组都 5/5，差值 0，样本太小，说明不了什么。
- agent-ab 是唯一能回答这个问题的实验，至今没有跑出评分过的运行；`eval/truth/agent-ab/pilot-v1` 里有计划、任务和提示词，transcripts 里没有已评分的运行，`infra-errors.jsonl` 只有 242 字节，应是 2026 年 10 月 23 日那次启动失败。

## 最小核心有多大

`impact` + `affected-tests` + 依赖图 + 缓存 + 共改的 require 闭包是 93 个文件、22,700 行，占 `src/` 的 55%；整个 container 的闭包是 141 个文件、31,600 行（77%）。瓶颈在 `dep-graph.js` 自己，它的闭包就有 82 个文件、20,000 行。所以只删命令砍不了多少。收敛到 6 种语言并去掉诊断、概览、安全等外围后，可到 15,000 至 20,000 行（估算）。

## 与同类方法对比

只有公开资料，没有同一 agent 同一基准的受控对照，来源多为论文与厂商自述，未核对原文：

- 一篇 arXiv 论文（2606.22417）报告结构化索引相对 agentic grep 的 resolve 率是 50.4% 对 41.9%（p=0.003），增益主要在改动涉及 3 个以上文件的任务。
- 一个厂商对照里 aider repo map 是 36.7%，不用检索是 35.0%，几乎没有差别。
- 本工具独特的是 git 共改、diff-context 和测试映射。朴素方法（`git log`、grep、读 diff）大多能替代，笨基线本质就是这类方法，工具只比它高 15 个百分点，还只在一个仓库的 20 个提交上成立。不好替代的只有「已知改动文件加 diff，得到引用方」和「改动文件，得到该跑哪些测试」两点。

## 三条路线

| 路线 | 利 | 弊 |
|---|---|---|
| (a) 砍到最小核心 | 维护面缩到约一半，文档与测试负担大降，符合项目自己写的「克制」 | 没有 agent-ab 结论就砍，依据只是直觉；砍法不当会丢掉 J1 仍在用的功能 |
| (b) 继续现状 | 无 | 新增 token 买不到可测量的收益，算法通道已关，剩下的只是维护和文档 |
| (c) 冻结新功能，只留 agent-ab 当闸门 | 约 34 美元就能得到唯一有分量的答案；设计文档里的判定线事先写死（差值不小于 5 个百分点且 95% 区间下界大于 0 为有增量，上界小于 5 个百分点为无增量） | 离线实验没有任务意图，「有增量」证明不了真实改代码时漏改变少 |

推荐 (c)：先跑预实验，有增量就小投入，没增量就走 (a)。判定阈值本身是判断，不是测出来的。

仍待项目所有者决定：预实验的运行凭据（见 [agent-offline-ab.md](../experiments/agent-offline-ab.md) 第 10 节）、F1 留出池给不给本实验、要不要在 J1 与 F1 业务仓库拉取新提交。
